# 按来源自动发现新视频

## 作者与播放列表的区别

| 来源 | 发现策略 |
| --- | --- |
| 作者 `/videos`、`/streams` | 沿用最近投稿/回放候选扫描，数量由候选数和最新N决定；直播、预告和处理中内容按原规则跳过 |
| 播放列表 | 每次获取完整可见平面清单，比对视频ID；首次只按当前顺序收录有效候选数量，其余历史ID仅作基线；此后开头、中间、末尾新增的视频均进入持久待收录队列 |
| 单视频 | 本轮不改动其发现及回放等待逻辑 |

作者不会因此改为全历史遍历；若同步间隔内投稿超过候选数，仍可能漏掉较早投稿，可缩短同步间隔或提高候选数。播放列表的“候选数量”改为首次和每批收录数，仍为1–100，有效值至少为频道最新N；检测清单的长度不再被这个数量截断。

例如已有150条的列表、候选数30：首次只收录前30条，剩余120条记入历史基线；下一次在任意位置新增65条，分30、30、5条收录。未收录历史不会因重排、调整候选数或重复同步自动补齐。已发现ID不会因移出再加入而当作全新视频重新下载；仍待收录的ID重新出现时可继续处理。

正常扫描沿用频道同步间隔（默认6小时）；有当前可见的待收录积压时，下一轮设为15分钟后，由Cron检查并排队，实际还受队列、限流与执行器在线状态影响。手动“立即同步”同样适用。发现不等于一定转码：最新N、配额、保留策略等继续生效。

## 一致性与失败处理

- 全部清单成功取回并校验后才建立基线。清单与持久待收录队列保存在D1，执行器换机或中断不丢失已经发现但未提交的ID。
- 每批结果须匹配本租约已选中的ID，节目写入、待收录确认和任务完成在同一批事务中提交。过期租约不能确认或消耗队列。
- 列表重排更新以该来源为排序归属的已有节目位置，保持原加入顺序和已有音频；列表删除项不会删除已收录节目。来源本身被删除时，其发现账本随来源清理。
- 空列表也可建立空基线；正在直播、处理中和私密不可见条目不进入本次可收录清单，之后变为可收录状态时可被发现。这里只能比对当前凭据与YouTube返回的可见条目。
- 平面清单最多10000条，元数据文件最多32MB。超过上限、已知总数大于返回条数或提取失败时，不以截断结果推进基线。极大列表需拆分；没有承诺无限长度或任意上游异常下的完整性。
- 首次基线对每个ID写入一条小记录，后续仅新增ID和位置变化产生相应写入；历史ID账本随列表累计增长，应结合D1读写与存储额度控制来源规模。

## 执行器升级与迁移

新增 `0016_source_discovery.sql`，不修改旧迁移。增加来源发现账本、初始化标记、任务批次/租约信息和 `discovery_control_version`。既有播放列表以升级后的第一次完整扫描建立基线，保留已有节目与音频；本轮不会自动补齐原扫描范围以外的历史。

新执行器上报 `X-Executor-Discovery-Control: 1`，Worker仅把播放列表扫描交给具备该能力的执行器；旧执行器仍可处理原有兼容作者/单视频任务。发布顺序：应用迁移，发布Worker/静态资源和新ZIP，等待本机执行器空闲后升级并恢复原暂停策略。未升级的其他机器需自行更新，不能把Worker发布等同所有执行器已升级。
